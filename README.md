# Mini NPU: MAC 패턴 판별기

표준 라이브러리만 사용하는 Python 3.8+ 기반 콘솔 프로그램입니다.

입력 패턴과 필터를 위치별 곱셈-누산(MAC, Multiply-Accumulate) 연산으로 비교하여 십자가(Cross)와 X 패턴을 판별합니다.

3×3 사용자 입력부터 5×5, 13×13, 25×25 JSON 데이터 분석까지 지원하며, 2차원 및 1차원 MAC 구현의 성능도 비교합니다.

---

## 1. 실행 방법

### 개발 환경

- Python 3.8 이상
- 외부 라이브러리 사용 금지
- Python 표준 라이브러리만 사용 (`json`, `time`, `re`, `math`, `statistics` 등)

### 실행 명령어

```bash
python main.py
```

실행 후 원하는 모드를 선택합니다.

| 선택 | 기능 | 설명 |
|---|---|---|
| 1 | 사용자 입력 모드 | 3×3 필터 A, B와 패턴을 직접 입력 |
| 2 | JSON 분석 모드 | data.json의 여러 케이스를 일괄 분석 |

JSON 분석 모드에서 파일 경로를 입력하지 않으면 `main.py`와 같은 폴더의 `data.json`을 읽습니다.

### 사용자 입력 방법

필터 A, 필터 B, 패턴 순서로 입력합니다.

각 행에는 숫자 3개를 공백으로 구분하여 입력합니다.

예시:

```text
0 1 0
1 1 1
0 1 0
```

다음과 같은 입력 오류가 발생하면 오류 유형에 맞는 안내를 출력하고 행렬 전체를 다시 입력받습니다.

- 열 개수 불일치
- 숫자 파싱 실패
- NaN 및 무한대 입력

## 2. 구현 요약

### 2-1. 데이터 구조

입력 패턴과 필터는 2차원 리스트로 저장합니다.

`matrix[row][column]` 형식으로 특정 위치의 값을 읽고 쓸 수 있습니다.

- 사용자 입력 모드: 3×3
- JSON 분석 모드: 5×5, 13×13, 25×25

### 2-2. MAC 연산 구현

MAC(Multiply-Accumulate)은 두 배열의 동일한 위치에 있는 값을 곱한 뒤 모든 결과를 누적하는 연산입니다.

수식:

```text
score = Σ(pattern[i][j] × filter[i][j])
```

예를 들어 십자가 패턴과 십자가 필터를 비교하면 다음과 같습니다.

입력 패턴:

```text
0 1 0
1 1 1
0 1 0
```

십자가 필터:

```text
0 1 0
1 1 1
0 1 0
```

위치별 곱셈 결과:

```text
0 1 0
1 1 1
0 1 0
```

최종 MAC 점수는 5입니다.

X 필터와 비교하면 점수는 1이므로 십자가 필터와 더 높은 유사도를 보입니다.

### 2-3. 2차원 및 1차원 MAC 비교

두 가지 방식으로 MAC 연산을 구현했습니다.

| 함수 | 구현 방식 |
|---|---|
| `mac_2d` | 2차원 리스트의 행과 열을 순회 |
| `mac_flat` | 2차원 배열을 길이 N²의 1차원 배열로 변환하여 순회 |

두 구현 모두 외부 라이브러리 없이 반복문으로 직접 구현했습니다.

동일한 데이터를 사용하여 두 방식의 연산 결과와 실행 시간을 비교할 수 있습니다.

MAC 점수는 별도 정규화나 분류 임계값을 적용하지 않은 유사도 합입니다.

### 2-4. 패턴 생성기

`generate_pattern(N, "Cross")`와 `generate_pattern(N, "X")`를 통해 크기 N의 패턴을 자동 생성합니다.

- Cross: 중앙 행과 중앙 열을 1로 설정
- X: 두 대각선 방향의 값을 1로 설정

생성된 패턴은 성능 측정 등에 재사용합니다.

### 2-5. 라벨 정규화

`normalize_label` 함수를 별도로 구현하여 입력 표기를 표준 라벨로 변환합니다.

| 입력 표기 | 정규화 결과 |
|---|---|
| `+` | Cross |
| `cross` | Cross |
| `Cross` | Cross |
| `x` | X |
| `X` | X |

앞뒤 공백을 제거하고 소문자로 변환한 뒤 표준 라벨을 반환합니다.

지원하지 않는 표기는 `None`으로 반환하여 JSON 케이스의 FAIL 사유로 처리합니다.

정규화 함수를 분리함으로써 사용자 입력 모드와 JSON 분석 모드에서 동일한 표기 규칙을 사용할 수 있도록 구성했습니다.

새로운 라벨을 추가할 때도 하나의 함수에서 규칙을 확장할 수 있습니다.

### 2-6. JSON 스키마 검증

JSON 케이스의 키는 다음 형식을 사용합니다.

```text
size_{N}_{idx}
```

정규식을 사용하여 키에서 N을 추출하고, 해당 크기에 맞는 `filters.size_N`을 선택합니다.

검증 항목:

- 케이스 키 형식
- input 및 expected 필드 존재 여부
- 필터 라벨 유효성
- 입력 패턴의 정방형 구조
- 패턴과 필터의 크기 일치 여부

잘못된 키, 필드, 라벨 또는 배열이 발견되면 해당 케이스만 FAIL 처리합니다.

전체 프로그램이 중단되지 않도록 케이스별 오류를 분리하여 처리합니다.

오류 출력 예시:

```text
size_5_3: 입력 배열 크기 불일치
size_13_4: 지원하지 않는 expected 라벨
size_invalid: 케이스 키 형식 오류
```

## 3. 점수 비교 및 동점 처리 정책

부동소수점 연산에서는 미세한 오차가 발생할 수 있습니다.

예를 들어 실제로 동일한 결과라도 다음과 같이 표현될 수 있습니다.

```text
0.9
0.8999999999999999
```

이러한 미세한 차이로 판정 결과가 달라지는 것을 방지하기 위해 허용오차(EPSILON)를 적용했습니다.

```python
EPSILON = 1e-9
```

두 점수의 차이의 절댓값이 EPSILON보다 작으면 동점으로 처리합니다.

```python
abs(score_a - score_b) < EPSILON
```

비교 연산자는 엄격한 `<`를 사용합니다. 따라서 차이가 정확히 1e-9라면 동점이 아니라 점수가 높은 쪽으로 판정합니다.

### 모드별 판정 정책

| 구분 | 사용자 입력 모드 | JSON 분석 모드 |
|---|---|---|
| 첫 번째 점수 우세 | A | Cross |
| 두 번째 점수 우세 | B | X |
| epsilon 이내 동점 | UNDECIDED | UNDECIDED |
| expected 비교 | 없음 | PASS / FAIL |

두 모드 모두 동일한 epsilon 규칙을 적용합니다.

차이점은 사용자 입력 모드에서는 필터 이름 A/B로 결과를 출력하고, JSON 모드에서는 표준 라벨과 expected를 비교한다는 점입니다.

**중요:** JSON 모드에서 UNDECIDED는 expected의 Cross 또는 X와 일치하지 않으므로 FAIL로 처리합니다.

EPSILON은 절대 허용오차입니다. 제공 데이터의 최대 점수 52.9를 기준으로 약 1.9×10⁻¹¹ 수준의 상대적인 크기입니다.

입력값의 크기나 범위가 크게 달라진다면 허용오차를 다시 검토해야 합니다. 특히 큰 값과 작은 값이 혼재하는 경우 상대오차 적용도 고려할 수 있습니다.

## 4. 성능 분석 및 시간 복잡도

### 4-1. 측정 방법

각 크기에서 동일한 패턴과 필터를 사용하여 MAC 연산 시간을 측정합니다.

측정 방식:

1. 3회 예비 실행으로 워밍업합니다.
2. MAC 함수를 10회 반복 측정합니다.
3. 평균 실행 시간과 표본 표준편차를 계산합니다.
4. 2차원 및 1차원 구현 결과를 각각 출력합니다.

측정에서는 행렬 생성, 평탄화, 파일 입출력 시간을 제외하고 MAC 함수 호출 구간만 측정합니다.

표준편차는 시스템 부하 등에 따른 실행 시간의 변동을 확인하기 위한 참고값입니다.

실행 시간이 짧은 경우 측정 환경에 따라 결과가 달라질 수 있습니다.

### 4-2. 연산 횟수 및 실제 측정 결과

각 행렬 크기에서 수행하는 MAC 연산 위치 수는 N²입니다.

| 크기 | MAC 연산 위치 수 (N²) |
|---|---:|
| 3×3 | 9 |
| 5×5 | 25 |
| 13×13 | 169 |
| 25×25 | 625 |
| 1000×1000 | 1,000,000 |

실제 터미널에서 측정한 성능 분석 결과입니다.

**측정 조건: 워밍업 3회, 본 측정 10회, 평균 및 표본 표준편차**

| 크기 | 2차원 평균±표준편차(ms) | 1차원 평균±표준편차(ms) | MAC 횟수 |
|---|---:|---:|---:|
| 3×3 | 0.001765±0.000434 | 0.001047±0.000056 | 9 |
| 5×5 | 0.003194±0.000168 | 0.002098±0.000072 | 25 |
| 13×13 | 0.016512±0.000212 | 0.011764±0.000247 | 169 |
| 25×25 | 0.121936±0.194457 | 0.172291±0.394915 | 625 |

실제 측정 결과 3×3, 5×5, 13×13에서는 1차원 구현의 평균 실행 시간이 더 짧았습니다.

반면 25×25에서는 2차원 구현의 평균 실행 시간이 더 짧게 측정되었습니다.

특히 25×25에서는 표준편차가 평균 실행 시간보다 크게 나타났습니다. 이는 짧은 실행 시간 측정에서 시스템 부하 등의 영향을 받았을 가능성이 있으므로 해당 결과만으로 2차원 구현이 더 빠르다고 일반화하기는 어렵습니다.

따라서 특정 자료구조가 항상 빠르다고 단정하기보다는 동일한 환경에서 반복 측정한 결과를 기준으로 판단해야 합니다.

### 4-3. 시간 복잡도 분석

한 번의 MAC 연산은 N×N 배열의 모든 위치를 한 번씩 방문합니다.

따라서 시간 복잡도는 다음과 같습니다.

```text
O(N²)
```

예를 들어 25×25 행렬은 총 625개의 위치를 처리하지만, 1000×1000 행렬은 1,000,000개의 위치를 처리합니다.

이는 25×25에 비해 연산 위치 수가 1,600배 증가한 것입니다.

따라서 행렬의 크기가 커질수록 Python 반복문에서 처리해야 하는 곱셈-누산 연산도 증가합니다.

### 4-4. 메모리 복잡도

패턴과 필터는 각각 N²개의 원소를 저장하므로 메모리 복잡도는 O(N²)입니다.

이 프로그램은 2차원 배열과 1차원 평탄화 복사본을 함께 사용합니다.

따라서 1차원 비교를 위해 추가적인 O(N²) 메모리가 필요합니다.

Python 리스트와 숫자 객체는 별도의 메모리 오버헤드가 발생하므로 원소 개수만으로 실제 메모리 사용량을 정확하게 판단할 수는 없습니다.

### 4-5. 대규모 데이터 최적화 방향

대규모 데이터를 처리할 경우 다음과 같은 최적화 방법을 고려할 수 있습니다.

- 실제 실행 환경에서 프로파일링하여 병목 구간 확인
- 1차원 평탄화가 반복 계산에 유리한지 실측
- 메모리 사용량 감소를 위해 `array('d')`와 같은 연속형 저장소 검토
- 데이터가 메모리보다 큰 경우 블록 단위 처리
- 필요한 경우 메모리 매핑을 통한 부분 데이터 접근

다만 특정 방식이 항상 빠르다고 가정하지 않고 실제 측정 결과를 기준으로 최적화 방향을 결정해야 합니다.

### 4-6. CPU와 NPU의 차이

일반적인 CPU는 복잡한 명령과 분기, 범용 작업을 효율적으로 처리하는 데 강점이 있습니다.

반면 NPU는 AI 연산에서 자주 사용되는 대량의 MAC 연산을 병렬로 처리하도록 설계된 전용 프로세서입니다.

NPU는 여러 연산을 동시에 수행하여 높은 산술 처리량을 확보할 수 있습니다.

그러나 연산 유닛에 데이터를 제때 공급하지 못하면 메모리 대역폭과 데이터 이동이 병목이 될 수 있습니다.

실제 NPU는 전용 메모리 계층, 데이터 타일링, 스케줄링 등을 활용하여 이러한 문제를 줄입니다.

이 프로그램은 MAC 연산의 기본 원리를 이해하기 위한 CPU 기반 콘솔 시뮬레이터이며 실제 NPU의 하드웨어 구조나 CPU/NPU 실측 성능 차이를 구현한 것은 아닙니다.

## 5. 실제 실행 결과 및 리포트

### 5-1. 3×3 사용자 입력 모드

십자가 필터 A와 X 필터 B를 생성하고 십자가 패턴을 입력하여 판별한 결과입니다.

**실제 터미널 출력**

```text
Mini NPU MAC 패턴 판별기
1) 사용자 입력 3×3
2) data.json 일괄 분석
선택 (1/2): 1

필터 A: 3개 행을 입력하세요 (각 행 3개 숫자, 공백 구분)
1행> 0 1 0
2행> 1 1 1
3행> 0 1 0

필터 B: 3개 행을 입력하세요 (각 행 3개 숫자, 공백 구분)
1행> 1 0 1
2행> 0 1 0
3행> 1 0 1

필터 A/B 저장 완료

입력 패턴: 3개 행을 입력하세요 (각 행 3개 숫자, 공백 구분)
1행> 0 1 0
2행> 1 1 1
3행> 0 1 0

점수 A: 5 | 점수 B: 1
연산 시간: 0.019747 ms | 판정: A

성능 분석 (워밍업 3회 후 10회 평균±표준편차):
3x3 2차원 0.004400±0.008338 ms,
1차원 0.000996±0.000131 ms, MAC 9회
```

**결과 분석**

- 필터 A는 십자가 형태이며 입력 패턴과 동일합니다.
- 필터 B는 X 형태입니다.
- MAC 연산 결과 A는 5, B는 1입니다.
- 점수 A가 더 높으므로 최종 판정은 A입니다.

입력 패턴과 동일한 형태의 필터가 더 높은 MAC 점수를 얻는 것을 확인했습니다.

### 5-2. JSON 일괄 분석 모드

제공된 `data.json`의 5×5, 13×13, 25×25 데이터 총 6개 케이스를 분석했습니다.

**실제 터미널 출력**

```text
Mini NPU MAC 패턴 판별기
1) 사용자 입력 3×3
2) data.json 일괄 분석
선택 (1/2): 2

data.json 경로 (Enter는 /workspaces/codysseypre3-mini-npu-mac-simulator/data.json):

[케이스별 판정]
size_5_1  | Cross=0.9  X=0.9  | 판정=UNDECIDED expected=X     | FAIL (판정 UNDECIDED != expected X)
```

### 5-4. FAIL 케이스 원인 분석

이번 분석에서 발생한 FAIL은 단순한 프로그래밍 오류가 아니라 필터의 점수 설계상 패턴을 구분하지 못하는 문제와 관련이 있습니다.

**① size_5_1**

```text
Cross=0.9
X=0.9
판정=UNDECIDED
expected=X
결과=FAIL
```

Cross와 X 필터의 점수가 각각 0.9로 계산되었습니다.

두 점수의 차이가 epsilon보다 작으므로 UNDECIDED로 판정되었습니다.

expected는 X이지만 프로그램이 두 필터 중 어느 쪽이 더 유사한지 구분할 수 없으므로 FAIL 처리됩니다.

**② size_13_2**

```text
Cross=7.5
X=7.5
판정=UNDECIDED
expected=Cross
결과=FAIL
```

Cross 패턴을 입력했지만 Cross 필터와 X 필터의 점수가 모두 7.5로 계산되었습니다.

X 필터의 중앙 가중치와 Cross 필터의 점수 구조가 동일한 결과를 만들어 두 필터의 구분력이 부족한 사례입니다.

expected는 Cross이지만 동점이므로 UNDECIDED가 반환되어 FAIL 처리됩니다.

**③ size_25_1**

```text
Cross=4.9
X=4.9
판정=UNDECIDED
expected=X
결과=FAIL
```

대각선 형태의 입력 패턴에서 Cross와 X 필터의 점수가 동일하게 계산되었습니다.

따라서 epsilon 비교 결과 UNDECIDED가 반환되었으며 expected인 X와 일치하지 않아 FAIL 처리되었습니다.

### 5-5. 실패 원인 분리 및 개선 방향

실패가 발생했을 때 원인을 다음 세 가지로 구분하여 분석했습니다.

| 구분 | 확인 사항 | 개선 방향 |
|---|---|---|
| 데이터/스키마 문제 | 키 형식, 필드 누락, 배열 크기, 라벨 | JSON 구조 및 입력 데이터 수정 |
| 로직 문제 | MAC 계산 및 2D/1D 결과 일치 여부 | 작은 행렬의 수동 계산과 비교 |
| 수치 비교 문제 | 점수 차이와 epsilon 적용 여부 | 허용오차 및 비교 정책 검토 |

특히 이번 데이터에서는 점수 차이가 epsilon 이내에 들어오는 케이스가 확인되었습니다.

예를 들어 0.9와 0.8999999999999999처럼 미세한 차이가 발생하더라도 1e-9보다 작다면 동점으로 처리합니다.

따라서 epsilon을 제거하여 억지로 PASS를 만들기보다는 두 필터가 실제로 서로 다른 점수를 낼 수 있도록 데이터와 필터 가중치를 개선하는 것이 더 적절하다고 판단했습니다.

## 6. 향후 개선 방향

이번 구현을 바탕으로 다음과 같은 개선을 고려할 수 있습니다.

## 7. 마무리

이번 과제를 통해 단순히 두 배열을 곱하고 더하는 MAC 연산뿐 아니라, 데이터의 구조를 검증하고 부동소수점 오차를 고려하여 판정 결과를 설계하는 과정까지 경험할 수 있었습니다.

특히 FAIL이 발생했을 때 결과를 임의로 수정하지 않고 데이터/스키마 문제, 로직 문제, 수치 비교 문제로 나누어 원인을 분석하는 것이 중요하다는 점을 배웠습니다.

또한 2차원과 1차원 구현을 직접 비교하면서 자료구조와 메모리 접근 방식이 성능에 미치는 영향을 생각해 볼 수 있었습니다.

이번 Mini NPU 시뮬레이터를 통해 AI 연산의 기본이 되는 MAC의 원리와 CPU 및 NPU의 처리 방식 차이를 이해하는 계기가 되었습니다.
